## 1. 背景与目标

guonl-spring-ai-flow 是一个可视化 AI 流程编排平台：用户在画布上拖拽 13 种节点（文本理解、图片识别、JSON/Excel 处理、条件路由、工具调用、知识检索、图片生成、内容审核、输出评估、子流程、聚合）编排 DAG，提交运行得到结果。

当前使用门槛集中在三处：

| 门槛 | 现状痛点 |
| --- | --- |
| 编排学习成本 | 13 种节点、变量协议（`{{input}}`、`{{nodeId.json.字段}}`）、条件路由规则需要阅读文档才能上手 |
| 提示词编写 | 节点 prompt 质量直接决定流程效果，新手难以写出结构化、带输出契约的提示词 |
| 失败排查 | 运行失败需要到「运行历史」逐节点看日志，定位是提示词、模型还是输入的问题 |

**AI 助手的目标**：在平台内提供一个「懂这个产品」的对话助手——既能**答疑**（基于产品知识）、又能**动手**（查流程/建流程/查运行）、还能**诊断**（分析失败原因）与**优化**（提示词改进建议），降低编排门槛、缩短排障路径。

## 2. 核心定位（已确认）

**全能助手**：一个入口覆盖四类能力，通过统一的对话交互（流式输出 + 多轮记忆）呈现。

```
┌─────────────────────── AI 助手 ───────────────────────┐
│                                                       │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌───────┐ │
│   │ 答疑顾问 │  │ 编排助理 │  │ 运行诊断 │  │ 提示词 │ │
│   │ 产品怎么用│  │ 查/建流程│  │ 失败原因 │  │  优化  │ │
│   └────┬─────┘  └────┬─────┘  └────┬─────┘  └───┬───┘ │
│        │             │             │            │     │
│        ▼             ▼             ▼            ▼     │
│   ┌───────────── 产品知识 + 工具调用 + 多轮记忆 ─────┐ │
│   └──────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘
```

### 2.1 四大能力详解

**① 答疑顾问（产品问答）**

- 回答「怎么用」类问题：节点类型说明、变量协议写法、条件路由规则、知识库/RAG 配置、MCP 接入方式、常见报错（对应 usage.md FAQ）。
- 知识来源：**系统提示词内嵌产品手册摘要**（13 节点速查表 + 变量协议 + FAQ 精简版），而非独立文档 RAG——手册总量可控（万字级），内嵌即可获得高质量回答，避免引入向量检索的额外链路与延迟。
- 若用户问题涉及「当前平台里有哪些流程/某流程长什么样」等事实数据，助手自动转工具调用获取真实数据作答。

**② 编排助理（查流程 + 建流程）**

- 查：自然语言查询流程列表（「有哪些和 Excel 有关的流程」）、查看某流程定义详情（节点/连线/提示词）。
- 建：**自然语言生成流程**——用户描述需求（「做一个：读 Excel → 提取关键字段 → 生成图片海报」），助手生成流程 JSON 并调用写工具保存，返回流程链接供用户到画布打开继续编辑。
- 建流程采用「**生成 → 保存 → 给出可点击链接**」闭环；生成前助手会与用户确认关键节点设计（多轮），避免一次跑偏。

**③ 运行诊断（失败分析）**

- 用户粘贴 runId 或说「刚才那个流程失败了，帮我看看」，助手调用只读工具获取运行详情（状态、各节点执行记录、错误信息、耗时、token 消耗），结合节点定义给出归因分析：
  - 提示词问题（如变量引用了不存在的上游）
  - 模型问题（如 429/超时/输出不符合 JSON 契约）
  - 输入问题（如 Excel 列缺失、图片不可达）
- 并给出修复建议（改哪个节点的 prompt / 换模型 / 加重试）。

**④ 提示词优化**

- 用户贴出某节点 prompt + 期望效果，助手输出改进版：结构化（角色/任务/约束/输出格式）、补输出契约（OutputSpec JSON Schema）、明确变量引用。
- 可结合②：优化后直接生成/更新流程。

### 2.2 明确不做（边界）

- 不做多租户/账号体系（沿用平台现状，无登录态）。
- 不做助手自身的长期人格记忆（会话内记忆即可，跨会话不记忆用户偏好）。
- 不替用户执行流程运行（可发起建议，但「提交流程运行」等高危写操作不做，防止误触发消耗）。
- P0 不做语音输入、图片上传到助手对话（后续可扩展）。

## 3. 呈现形态（已确认）

**全局悬浮窗 + 独立会话页** 双入口，共享同一套后端与会话数据。

### 3.1 全局悬浮窗（聊天抽屉）

- 全站右下角固定悬浮按钮（含 AI 图标，主题跟随 `common.js` 的主题系统），点击展开聊天抽屉（约 400×560px）。
- 注入方式与全局 footer 一致：**由 `common.js` 单点注入，7 个页面零侵入**。
- 抽屉内支持：多轮对话、SSE 流式渲染、markdown 轻量渲染（代码块/表格/列表）、会话切换、新建会话。
- 编辑器页（/flow-editor）悬浮窗同样可用，方便边编排边问。

### 3.2 独立会话页（/assistant）

- 侧栏新增「AI 助手」入口（编排分组下），路由 `/assistant`。
- 宽屏三栏：左侧会话历史列表（可重命名/删除）+ 中间对话主区 + 右侧「快捷能力」面板（预置提问卡片：介绍节点类型 / 帮我建流程 / 诊断一次运行 / 优化提示词）。
- 独立页与悬浮窗共用 conversationId 体系——悬浮窗里开的会话在独立页可见可续聊。

### 3.3 交互细节

- 流式输出：SSE 逐 token 渲染，光标闪烁；工具调用阶段显示「正在查询流程列表…」状态行，完成后折叠展示工具轨迹（调用了什么工具、返回摘要）。
- 消息气泡：用户右侧、助手左侧；助手消息支持复制、重新生成（P1）。
- 会话标题：取首条用户消息前 40 字符，自动生成（不调 LLM，遵循 YAGNI）。
- 错误兜底：模型异常/网络中断给出可读错误并支持「重试」；mock 模式下页面顶部显示「当前为 Mock 助手」标识（复用 providerPill 机制）。

## 4. 整体架构

```
┌────────────────────────── 前端（原生 JS，无 npm） ──────────────────────────┐
│  common.js 注入悬浮窗   │   /assistant 独立页（Thymeleaf 模板）             │
│        └──────────────── assistant-chat.js（共享核心：SSE/渲染/会话管理）──┘ │
└──────────────────────────────────┬─────────────────────────────────────────┘
                                   │ POST /api/assistant/chat (SSE)
                                   │ GET/POST/DELETE /api/assistant/sessions…
┌──────────────────────────────────▼─────────────────────────────────────────┐
│  AssistantController（SSE + 会话 CRUD）  →  AssistantSessionService         │
│                                                   │                        │
│  AssistantService（编排入口）                       │                        │
│   ├─ provider=llm  → AiInvoker.stream（挂 assistant 工具集 + 会话记忆）     │
│   └─ provider=mock → 意图路由（关键词分类）+ 真实工具调用 + 模板化回答        │
│                                                                          │
│  AssistantTools（助手专用 @Tool 集合）                                      │
│   ├─ list_flows / get_flow        （只读·流程）                            │
│   ├─ get_run / recent_run_errors  （只读·运行）                            │
│   ├─ search_knowledge             （只读·知识库检索）                       │
│   └─ save_flow                    （写·NL 生成流程，P1）                    │
│                                                                          │
│  复用层：AiInvoker SPI / SPRING_AI_CHAT_MEMORY（JDBC 会话记忆）/ FlowStore  │
│         RunStore / KnowledgeService（向量检索）                            │
└──────────────────────────────────┬─────────────────────────────────────────┘
                                   │
                        MySQL（assistant_session + SPRING_AI_CHAT_MEMORY）
```

**关键架构决策**：

1. **助手工具集独立于流程执行工具集**：现有 `useTools` 仅挂载内置 `FlowTools`（时间/计算/抓取/JSON 提取），服务的是 TOOL 节点。助手需要自己的 `AssistantTools`（查流程/查运行/检索知识库/建流程），通过扩展 `InvokeRequest` 按需挂载，互不干扰。
2. **复用 AiInvoker SPI 而非绕过**：助手不直接依赖 Spring AI 类型，沿用项目「业务层只认 AiInvoker」的既有原则；在 `InvokeRequest` 上扩展工具集选择（toolSet），`SpringAiInvoker` 与 `MockAiInvoker` 双实现同步升级。
3. **消息存储双轨**：模型对话记忆复用 `SPRING_AI_CHAT_MEMORY`（JDBC ChatMemory，已建表，按 conversationId 隔离）；会话元数据（标题/消息数/更新时间）落新表 `assistant_session`，供会话列表/跨页续聊。
4. **mock 模式不做死文案**：mock 助手走「意图路由（关键词分类）+ 真实工具调用 + 模板化回答」，即使无大模型，查流程/查运行等能力依然真实可用——与项目「mock 也要可演示完整链路」的既有风格一致。

## 6. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端框架 | Spring Boot 4.1.1 + Spring AI 2.0.1 | 与平台一致；直接复用 AiInvoker、ChatMemory、Tool Calling 基建 |
| 模型调用 | 现有 AiInvoker SPI（llm=SpringAiInvoker / mock=MockAiInvoker 双实现） | 沿用 provider 开关（`FLOW_AI_PROVIDER`），架构统一 |
| 会话记忆 | Spring AI JDBC ChatMemory（`SPRING_AI_CHAT_MEMORY` 表，已有） | 零新增存储方案，按 conversationId 隔离 |
| 会话元数据 | MySQL 新表 `assistant_session` + MyBatis XML Mapper | 沿用项目 *DO + Mapper 模式 |
| 实时输出 | SSE（`text/event-stream` + `SseEmitter`） | 与 RunStreamHub 流式推送同思路；无需 WebSocket |
| 工具调用 | Spring AI `@Tool` 注解（AssistantTools），复用 annotation-scanner | 与 FlowMcpToolCallbackProvider 同套机制 |
| 前端 | 原生 JS/CSS + Thymeleaf，markdown 自写轻量渲染 | 项目无 npm/构建链，保持零依赖 |
| 注入机制 | common.js 单点注入悬浮窗（同 footer 模式） | 全站 7 页零侵入 |

## 7. 非功能设计

- **性能**：流式首 token 目标 < 2s（llm）；工具调用轨迹实时回传避免长时间空等；`assistant_session` 查询走 conversation_id/updated_at 索引。
- **稳定性**：SSE 断连由前端 catch 并提示重试；模型调用超时沿用 `flow.ai.node-timeout-seconds` 同级配置（assistant 独立可配）；单条用户消息长度上限（如 4000 字）防滥用。
- **安全**：助手仅暴露白名单工具；`save_flow` 为唯一写工具且生成后需用户到画布确认；不做任意 SQL/任意文件访问；提示词中注入「工具结果仅作参考」防提示注入放大。
- **成本**：系统提示词手册摘要控制在 ~2K token；memoryTurns 默认 10 轮截断；mock 模式零模型成本可完整演示。
- **可配置**：新增 `flow.assistant.*` 配置节（开关/模型覆盖/温度/记忆轮数/悬浮窗开关），与 `flow.ai.*` 风格一致，默认继承全局模型。
